# 프롬프트: 컨텍스트 파일 활용 (목적별 3종)

> 용도: 사용자가 앱에서 컨텍스트 파일을 내보낼 때 함께 복사해 주는 프롬프트. 파일을 첨부(또는 본문에 붙여넣기)하고 아래 중 하나를 붙여 넣는다.
> 각 프롬프트는 "출력 형식 + 금지 + 불확실할 때"의 세 부분으로 되어 있다. **출력해야 할 것은 전부 "출력 형식" 절에 둔다.** 다른 절에 둔 출력 지시는 서비스에 따라 무시되는 것이 실험 01에서 확인됐다.
> 상태: **v0.2** (2026-11-01, 실험 01의 9회 채점 반영). 변경 내역은 문서 끝.

---

## A. 경력기술서

```text
첨부한 파일은 내 경력 데이터다 (형식: slow-way-career-context). 파일 상단의 "사용 안내"를 먼저 읽고 지켜 달라.

이 데이터로 경력기술서를 작성해 달라.

## 출력 형식 (아래 1~3을 이 순서로 전부 출력한다)

1. 경력기술서 본문
   - 맨 위에 요약: 현재 직위와 총 경력 1문장, 핵심 역량 3개를 각 1문장. 여러 과제에 걸친 횡단 경험(예: 경영층 발표 누적 건수)이 파일에 있으면 요약에서 역량 근거로 반드시 1회 언급한다.
   - 경력(회사·조직·직위) 단위로 역순 묶음. 묶음 안의 경험도 시간 역순.
   - 경험마다 다음 라벨만 쓴다: "기간", "역할", "상황과 목표"(2~3문장), "행동"(2~4개), "결과"(정량 먼저, 정성 다음).
   - 경험은 최대 8건. 상황·행동·결과가 모두 채워진 경험을 우선한다.
   - 본문 마지막에 "학력·특허·수상" 절을 두고 파일의 프로필 항목을 그대로 옮긴다. 확인 필요 여부와 관계없이 빼거나 바꾸지 않는다.
   - 문장은 "~했다"체. 각 문장 끝에 근거 경험 ID를 괄호로 남긴다. 예: (E-001)
2. [메모] 넣을지 물어볼 경험
   - 본문에 넣지 않은 경험 전부를 ID, 제목, 뺀 이유의 표로 적는다. 이 표는 문서의 일부가 아니라 나에게 주는 메모다.
3. [메모] 데이터 확인 요청
   - 작성 중 발견한 파일의 모순을 번호 목록으로 적는다. 예: 기간 겹침, 소속과 연도 불일치, 같은 사실의 다른 표기, 수치 불일치. 없으면 "없음".

위 1~3 외의 인사말, 설명, 제안 문장은 쓰지 않는다.

## 금지
- 파일에 없는 성과·수치·역할·직위·시점·도구·환경을 만들지 않는다.
- 역할은 파일의 역할 줄 그대로 쓴다. 파일에 "구현은 AI 코딩 도구"라고 있으면 "직접 구현했다"고 쓰지 않는다.
- "기준 없음"으로 표시된 수치에 개선·단축·증가·향상 같은 비교 표현을 붙이지 않는다.
- 파일의 "교훈"은 그 경험 안에서만 쓴다. 다른 경험의 원칙으로 일반화하지 않는다.
- 역량을 형용사로 꾸미지 않는다 ("탁월한", "뛰어난", "뼈아픈" 금지). 행동과 결과로 보여 준다.
- 본문에 "확인 필요"라는 말을 쓰지 않는다.

## 불확실할 때
- 파일의 "확인 필요"에 적힌 내용은 단정하지 않는다. 그 경험을 쓸 때는 확정된 부분만 쓰고, 해당 문단 바로 아래에 `[질문: …]` 한 줄을 둔다. 문장 안에 넣지 않는다.
- 어떤 경험을 넣을지 애매하면 넣지 말고 2번 메모에 적는다.

## 채용공고 (있으면)
(여기에 JD 붙여넣기. 없으면 이 절을 지운다.)
JD가 있으면 JD의 요구 역량 순서로 경험의 강조점을 조정하되, JD에 맞추려고 없는 경험을 만들지 않는다. JD 요구 중 데이터에 근거가 없는 항목은 3번 메모에 "근거 없는 요구 항목"으로 따로 적는다.
```

## B. 자기소개서 (역량 중심, 지원동기 제외)

```text
첨부한 파일은 내 경력 데이터다 (형식: slow-way-career-context). 파일 상단의 "사용 안내"를 먼저 읽고 지켜 달라.

이 데이터로 자기소개서의 "경력·역량" 부분을 작성해 달라. 지원동기와 입사 후 포부는 쓰지 않는다.

## 출력 형식 (아래 1~2를 이 순서로 전부 출력한다)

1. [메모] 선택한 역량 3개와 선택 이유
   - 파일의 "역량 색인"에서 관련 경험이 2개 이상인 역량을 우선한다. 역량마다 1줄로 이유와 관련 경험 ID를 적는다.
   - 이 메모는 문서의 일부가 아니다. 내가 바꾸고 싶으면 바꿀 수 있게 하는 것이 목적이다.
2. 자기소개서 본문
   - 소제목 3개. 각 소제목은 역량 하나를 대표하고, 그 아래 경험 1~2개를 이야기로 푼다.
   - 각 이야기는 "상황 → 내 판단과 행동 → 결과 → 그 경험이 남긴 것" 순서. 파일의 "교훈" 필드가 있으면 마지막 문장에 쓴다.
   - 분량: 소제목마다 공백 포함 600~800자, 전체 공백 포함 2,000~2,400자. 근거 ID와 [질문] 줄은 글자 수에서 뺀다. 상한을 넘기지 않는다.
   - 1인칭. "~했습니다"체. 각 문단 끝에 근거 경험 ID를 괄호로 남긴다.

위 1~2 외의 인사말, 설명, 제안 문장은 쓰지 않는다.

## 금지
- 파일에 없는 성과·수치·역할·시점을 만들지 않는다.
- 역할은 파일의 역할 줄 그대로 쓴다. 파일에 "구현은 AI 코딩 도구"라고 있으면 "직접 구현했다"고 쓰지 않는다.
- "기준 없음" 수치에 개선·단축·증가·향상 같은 비교 표현을 붙이지 않는다.
- 파일의 "교훈"은 그 경험 안에서만 쓴다. 다른 경험의 원칙으로 일반화하지 않는다.
- 감정·강조 표현("뿌듯했다", "뼈아픈", "귀중한", "전면")으로 분량을 채우지 않는다.
- 파일의 약어를 임의로 풀어 쓰지 않는다 (예: PBL을 Problem-Based Learning으로 확장하지 않는다).
- 본문에 "확인 필요"라는 말을 쓰지 않는다.

## 불확실할 때
- 파일의 "확인 필요"에 적힌 내용은 단정하지 않는다. 이야기를 완성하는 데 빠진 정보가 있으면 추정해 채우지 말고, 그 문단 바로 아래에 `[질문: …]` 한 줄을 두고 계속 쓴다. 문장 안에 넣지 않는다.

## 채용공고 (있으면)
(여기에 JD 붙여넣기. 없으면 이 절을 지운다.)
```

## C. 면접 예상 질문과 답변 근거

```text
첨부한 파일은 내 경력 데이터다 (형식: slow-way-career-context). 파일 상단의 "사용 안내"를 먼저 읽고 지켜 달라.

이 데이터를 바탕으로 면접관이 물을 만한 질문과, 각 질문에 답할 때 쓸 근거를 정리해 달라.

## 출력 형식 (아래 1~3을 이 순서로 전부 출력한다)

1. 예상 질문 15개. 유형별로 나눈다: 경험 검증(5) / 수치 검증(3) / 실패·갈등(3) / 리더십·판단(4).
   - 질문마다: 질문 / 왜 물을 것 같은가 1줄 / 답변 근거가 되는 경험 ID와 핵심 사실 3줄 이내 / 이 질문에서 약한 지점 1~2줄.
   - 답변 문장을 대신 써 주지 않는다. 근거와 약점만 정리한다.
   - 수치 검증 질문은 "정량 성과 목록"에서 비교 기준이 없거나 "확인 필요"인 항목을 우선 고른다.
   - 실패·갈등 질문은 파일에 실패나 종결로 적힌 경험이 있으면 그것을 쓴다. 없으면 "파일에 실패 사례가 없다"고 적고 질문만 제시한다.
   - 여러 과제에 걸친 횡단 경험(예: 경영층 발표 누적)이 파일에 있으면 질문 1개 이상의 근거로 쓴다.
2. 준비가 부족한 경험
   - 상황·행동·결과가 비어 있거나 "확인 필요"가 많은 경험 전부를 ID, 제목, 비어 있는 것, 면접에서 나올 계기의 표로 적는다. 나올 가능성이 높은 순서로 정렬한다.
3. 기준 없는 수치 목록
   - "정량 성과 목록"에서 비교 기준이 없는 수치를 ID와 함께 나열한다. 면접에서 "개선"이라고 말하면 안 되는 수치다.

위 1~3 외의 인사말, 설명, 제안 문장은 쓰지 않는다.

## 금지
- 파일에 없는 사실을 답변 근거로 제시하지 않는다. 질문 문장에도 파일에 없는 상황("설득하고", "부임 초기")을 넣지 않는다.
- 역할은 파일의 역할 줄 그대로 쓴다. 파일에 "구현은 AI 코딩 도구"라고 있으면 "직접 구현"이라고 쓰지 않는다.
- 파일의 "교훈"을 다른 경험의 원칙으로 일반화하지 않는다.
- 약점을 감추는 답변 요령을 쓰지 않는다. 약점은 약점으로 적는다.

## 불확실할 때
- 약한 지점에 파일 밖의 추론(예: 면접관이 이어서 물을 만한 것)을 쓸 때는 "추정:"을 앞에 붙여 파일 사실과 구분한다.
- 질문이 파일의 어느 경험에 해당하는지 애매하면 해당 ID 후보를 모두 적는다.
```

## 채점표 (실험용)

각 서비스 × 프롬프트별로 아래 네 기준을 0~2점으로 채점한다. 기록은 `docs/experiments/01_context_file_validation.md`.

| 기준 | 0 | 1 | 2 |
|------|---|---|---|
| 사실 정확성 | 없는 성과·역할을 만듦 | 과장 표현 있음 | 파일 사실만 사용 |
| 수치 보존 | 수치 변형·창작 | "기준 없음" 수치에 비교 표현 | 값·기준 그대로 |
| 형식 준수 | 지시 형식과 다름 | 일부 어김 | 지시대로 |
| 제출 가능성 | 다시 써야 함 | 손질하면 가능 | 거의 그대로 가능 |

## 변경 내역

### v0.2 (2026-11-01) — 실험 01 반영

공통
- 출력해야 할 항목을 전부 "출력 형식" 절로 모음. v0.1에서 "불확실할 때"·"역량 선택"에 있던 출력 지시(넣을지 물어볼 경험, 데이터 확인 요청, 역량 3개와 이유, 준비 부족 목록)를 ChatGPT·Gemini가 각각 다르게 빠뜨림.
- "문서 밖 문장 금지" 추가. Gemini가 문서 끝에 대화 문장을 붙임.
- 메모 성격의 출력([메모])을 문서와 구분하도록 명시.
- 역할 줄 그대로 쓰기 규칙 추가. Gemini가 "기획·검증, 구현은 AI 코딩 도구"를 "직접 구현"으로 격상 (3회).
- 교훈의 일반화 금지 추가. Gemini C가 E-004 교훈을 11건 발표의 원칙으로 확장.
- 미확정 항목은 본문에 "확인 필요"를 쓰지 않고 문단 끝 `[질문]` 줄로 통일. ChatGPT A는 본문에 "기간: 확인 필요"를 적었고, ChatGPT B는 문장 안에 [질문]을 넣어 문장이 깨짐.
- 횡단 경험을 반드시 1회 사용하도록 지시. 9회 중 ChatGPT·Gemini의 A·B·C 5회에서 E-009가 누락.

A
- 분량을 "A4 2~3장"에서 "경험 최대 8건"으로. 장 수 기준은 3개 서비스 모두 안 지킴.
- "학력·특허·수상" 절을 출력 형식에 명시. ChatGPT A에서 특허가 통째로 사라짐.
- 라벨 이름을 명시. Gemini가 "역할 한 줄"이라는 지시문을 라벨로 출력.

B
- 분량 기준을 "공백 포함"으로 명시하고 근거 ID·[질문]은 제외. v0.1은 기준이 없어 판정 불가.
- 약어 확장 금지 추가. Gemini가 PBL을 Problem-Based Learning으로 풀어 씀.

C
- "기준 없는 수치 목록"을 출력 3번으로 추가. Claude C가 자발적으로 만든 것이 유용했음.
- 약한 지점의 추론에 "추정:" 표시. Claude C의 추론형 약점(미탐 함정, 구현 주체 후속 질문)은 유용하나 파일 사실과 구분 필요.
- 질문 문장에 파일 밖 상황 금지. Gemini C의 "50명을 설득", "부임 초기".

### v0.1 (2026-11-01) — 초안
