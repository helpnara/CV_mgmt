## 1. 가장 먼저 할 일: 코드 없이 가설 검증 (1주)

컨텍스트 파일 방식의 핵심 가설은 **"잘 구조화된 커리어 파일을 사용자의 AI에 넣으면 실제로 쓸 수 있는 문서가 나온다"**이다. 앱을 만들기 전에 수작업으로 검증할 수 있다.

### 실험 절차

1. 본인의 실제 경력을 아래 2절의 파일 형식 초안대로 **수작업으로** 작성한다 (경험 15~30건).
2. 목적별 프롬프트 초안 3개를 쓴다: 경력기술서, 자기소개서(지원동기 제외 역량 중심), 면접 예상 질문.
3. 파일 + 프롬프트를 ChatGPT, Claude, Gemini에 각각 넣어 결과를 받는다. 웹과 iOS 앱 양쪽에서 시도한다.
4. 결과를 네 기준으로 채점한다: 사실 정확성(없는 성과를 만들었는가), 수치 보존(파일의 수치만 썼는가), 형식 준수, 실제 제출 가능 여부.
5. 파일 형식과 프롬프트를 2~3회 고쳐 가며 반복한다.

### 이 실험에서 확인할 것

- **구조화 프롬프트 왕복(D-008)도 함께 검증한다.** 자유 기록 한 줄을 구조화 프롬프트와 함께 AI에 넣고, 돌아온 결과가 정해진 형식을 얼마나 지키는지(파싱 가능 비율), 서비스별 차이, 형식을 어기는 전형적 패턴을 기록한다. 이 결과가 파서 설계를 결정한다.

- 파일을 첨부했을 때와 본문에 붙여 넣었을 때 결과 차이
- AI 서비스별 파일 첨부 지원 여부와 한도 (파일 크기, 파일 수, 토큰). 특히 **각 서비스의 iOS 앱이 공유 시트로 Markdown 파일을 받는지** 확인한다. 이것이 UX 설계를 결정한다.
- 과장 금지 지시문을 프롬프트에 넣었을 때 실제로 지켜지는 비율
- 경험이 많아질 때(100건 이상 가정) 파일을 분할해야 하는 지점

### 산출물

- 검증된 컨텍스트 파일 형식 v0.1
- 검증된 목적별 프롬프트 3개
- 서비스별 첨부 호환성 표
- 실험 기록 (`docs/experiments/01_context_file_validation.md`)

이 실험 결과가 나쁘면 앱 내 문서 생성(1번 출구)을 다시 올려야 하므로, 다른 준비보다 먼저 한다.

## 2. 커리어 컨텍스트 파일 설계 (07_EXPORT_DESIGN의 재료)

이 파일이 제품의 실제 산출물이므로 가장 공들여 설계해야 한다.

### 2.1 파일 구조 초안

```markdown
---
format: slow-way-career-context
version: 0.1
exported_at: 2026-10-01
owner: (이름 또는 익명)
scope: 전체 | 기간 | 선택 경험
anonymized: true | false
---

# 사용 안내 (AI에게)
- 이 문서는 사용자가 직접 기록하고 확정한 경력 데이터다.
- 여기에 없는 성과, 수치, 역할을 만들지 않는다.
- 수치는 문서에 적힌 값만 사용한다. 추정이 필요하면 사용자에게 질문한다.
- 요청받은 문서 형식을 따르되, 각 문장은 아래 경험 중 하나에 근거해야 한다.

# 프로필
# 경력 (회사 / 직위 / 기간, 역순)
# 프로젝트
# 경험 (STAR 구조, 확정된 것만)
  ## [E-023] 팀 과제 포트폴리오 및 진척 관리
  - 기간 / 조직 / 역할 / 소속 프로젝트
  - 상황 / 과제 / 행동 / 결과(정량, 정성, 비즈니스 영향)
  - 역량 태그
  - 원본 기록 요약 (선택)
# 역량 색인 (역량 → 관련 경험 ID)
# 정량 성과 목록 (수치 → 경험 ID)
```

### 2.2 결정할 사항

- **범위 옵션**: 전체 / 회사별 / 기간 / 직접 선택 / 확정 상태만(기본값)
- **익명화 옵션**: 회사명, 인명, 제품명, 고객명을 치환하고 치환표를 앱에 보관. 재직 중 이직 준비에 필수
- **원본 기록 포함 여부**: Entry 원문을 넣으면 AI가 더 풍부하게 쓰지만 파일이 커지고 민감정보 노출이 늘어남. 기본 제외, 옵션 포함
- **크기 전략**: 경험 1건 약 500~800 토큰(한국어). 100건이면 5만~8만 토큰. 서비스별 한도에 따라 회사별 분할 또는 "요약본 + 상세본" 두 파일 구조 검토
- **기계 가독 병행**: Markdown 외에 JSON 내보내기를 함께 제공할지. 백업·복원(A4) 용도로는 JSON이 필요하므로 두 형식을 같은 모델에서 직렬화
- **전달 경로**: 파일 저장(iOS Files), 공유 시트(AI 앱으로 직접), 클립보드(텍스트), AirDrop/메일
- **동반 프롬프트 전달 방식**: 파일 상단에 포함 / 별도 클립보드 복사 / 둘 다

### 2.3 목적별 프롬프트 템플릿 (초안 5종)

경력기술서, 이력서 요약, 자기소개서(역량 중심), 면접 예상 질문과 답변 근거, 승진·평가 자료. 각 템플릿은 "형식 지시 + 과장 금지 지시 + 불확실 시 질문 지시"의 세 부분으로 구성한다. 사용자가 채용공고(JD) 텍스트를 함께 붙일 수 있는 자리를 둔다.

## 3. 데이터 모델 확정 (04_DATA_MODEL)

컨텍스트 파일은 데이터 모델의 직렬화 결과이므로 모델이 먼저 정해져야 한다.

- [ ] Career → Project(선택) → Experience → Entry 4계층 확정
- [ ] Experience 상태 머신: 초안 → 구조화됨 → 확정. 내보내기 기본값은 확정만
- [ ] Experience 필드 확정 (01 문서 5장 기준, 정량 성과는 수치·단위·비교 기준을 분리 저장)
- [ ] Skill 사전 초안: 한국어 기본 역량 50~100개와 동의어 (예: 과제 관리 = 프로젝트 관리). 분류 축: 기술/업무/리더십/문제해결
- [ ] 용어집: Entry=기록, Experience=경험, Project=과제, Career=경력, Skill=역량, Evidence=증빙
- [ ] 스키마 버전과 마이그레이션 규칙 (10년 사용 전제)
- [ ] 안정적인 ID 체계 (컨텍스트 파일의 E-023 같은 참조에 쓰임)

## 4. 기록 단계 AI 준비 (06_AI_DESIGN)

- [ ] 구조화 출력 스키마 (JSON Schema). 모델이 자유 텍스트가 아닌 스키마에 맞는 결과를 내도록 구조화 출력 기능 사용

- [ ] 골든 세트: 한국어 입력 샘플 20~30개(한 줄, 긴 서술, 음성 전사체, 반복 업무, 진행 중 업무) + 기대 결과. 프롬프트를 바꿀 때마다 회귀 확인
- [ ] 모델 선택: 구조화는 소형 모델로 충분한지 골든 세트로 비교. 시스템 프롬프트 캐싱 적용
- [ ] 새 Entry가 기존 Experience의 업데이트인지 새 경험인지 판별하는 규칙과 사용자 확인 UX
- [ ] 선택 검토: 온디바이스 모델(Apple Foundation Models)의 한국어 구조화 품질 스파이크. 가능하면 1차 처리기로 승격

## 6. 개발 환경 (2026-10-02 개정: 느린 나이테 스택, D-006·D-008)
