## 3. 일의 양 비교

### 3.1 ①에서 생기는 일

| 일 | 양 | 통합 뒤에 남나 |
|----|----|----------------|
| 골격 복사·정리 (05 §2.1 약 20개 파일, §2.2의 `main` 490줄·`indexer` 985줄·`settings` 918줄 고쳐 쓰기) | 큼 | **버림.** 나이테에 이미 있다 |
| 안전망 (버전·휴지통·백업·오류 기록·검색) 다시 연결 | 중간 | **버림** |
| 별도 vault·스키마·설정·메뉴·배포 도구 | 중간 | **버림** |
| 느린 나이테 이력을 독립 앱으로 들여오는 통로 (팀원 데이터가 나이테에 있으므로 꼭 필요) | 중간 | **버림.** 통합하면 같은 DB를 직접 읽는다 |
| 느린 길 고유 기능 (경험 모델, 파서, 구조화 왕복, 정합성, 역량 매핑, 내보내기) | 큼 | 남음. 다만 통합 때 고쳐 넣어야 한다 |
| **통합 작업**: vault 배치(`people/<이름>/`), 스키마 합치기(22 + 1), 설정·메뉴·스타일 합치기, ID 바꾸기(P-nn → 나이테 과제 번호, profile → 명부), 시험 합치기, 그동안 쌓인 느린 길 데이터 옮기기 | 큼 | 일회성 |

M0 로드맵(08 §2) 14개 작업 중 0(골격)·11(안전망)·12(배포) 전부와 3·6(도메인 모델·프론트 골격)의 상당 부분이 통합 뒤 버려지거나 다시 하는 일이다. **대략 M0 일의 3분의 1 이상이 중복**이고, 여기에 통합 작업이 더해진다.

### 3.2 ②에서 생기는 일

| 일 | 양 | 비고 |
|----|----|------|
| 느린 길 설계를 나이테 언어로 옮기기 | 중간 | 04 모델, 스펙, 프롬프트, 실험 결과, 07 내보내기는 앱과 무관해 그대로 쓴다. 02·03·05·08은 독립 앱 기준이라 나이테 TODO 항목으로 다시 쓴다 |
| **사내 용어 규칙 맞추기** (나이테 238 ④ 금칙어 시험) | 작음~중간 | 느린 길 문서·프롬프트에는 구직 서류 이름이 많다(`decompose_cv` 등). 나이테로 넘길 때 "업무 이력 문서" 같은 말로 바꿔야 금칙어 시험을 통과한다 |
| 느린 길 고유 기능을 나이테 안에 | 큼 | ①과 같은 양. 다만 사람·과제·담당·회고가 이미 있어 **도메인 모델 일이 줄어든다** |
| 큰 코드베이스 안에서 일하는 비용 | 중간 | 바꿀 때마다 시험 930여 건, 나이테의 TODO·배포본·체크리스트 절차를 따른다 |

### 3.3 한눈에

| 기준 | ① 따로 → 통합 | ② 나이테 업그레이드 |
|------|---------------|---------------------|
| 전체 일의 양 | 큼 (중복 + 통합) | **작음** |
| 목표에 닿는 시간 | 김 (M0 → 통합까지 두 번 도착) | **짧음** |
| 실제 데이터로 검증 | 늦음 (가상 자료 → 들여오기 통로 → 통합) | **바로** (팀장 PC의 실제 팀 데이터. 저장소에는 여전히 가상 자료만) |
| 같은 일 두 번 (나이테 교훈 ②) | 생김 | 없음 |
| 운영 중인 시스템에 주는 위험 | 없음 (통합 전까지) | **있음** → 4절 대책 |
| 실험적 설계를 자유롭게 바꾸기 | 쉬움 | 나이테 절차 때문에 느림 |
| 느린 길을 나이테 없이 쓰기 (다른 팀, 개인) | 가능 | 어려움 |

## 4. ②의 위험과 대책

| 위험 | 대책 |
|------|------|
| 팀이 쓰는 시스템이 흔들린다 | 새 기능은 **팀장만 보이는 영역**으로 시작하고 기존 화면을 건드리지 않는다. 스키마는 추가만(나이테가 22번까지 해 온 방식) |
| 경험 모델·파서처럼 아직 다듬는 개념이 큰 코드 안에서 엉킨다 | 파일·DB·화면을 모르는 **순수 함수 모듈**을 나이테 안의 한 폴더에 따로 두고 시험부터 만든다(5절 1단계). 화면이 없으니 배포본에 드러나지 않는다 |
| 금칙어 | 넘기기 전에 용어 대응표를 만들고, 나이테 금칙어 시험을 그대로 돌린다 |
| 느린 길 저장소의 실험·설계가 흩어진다 | 느린 길 저장소는 **설계·실험·스펙의 원본**으로 남긴다. 나이테에는 구현과 TODO만 |

## 5. ②로 갈 때의 순서

| 단계 | 어디서 | 내용 | 끝나는 조건 |
|------|--------|------|-------------|
| 0 | 느린 길 저장소 | **이관 묶음**: 용어 대응표(금칙어), 04 모델을 나이테 엔티티(사람·과제·담당)에 맞춘 판, 나이테 TODO 항목 초안 | 사용자 검토 |
| 1 | 나이테 | 순수 함수 모듈 + 가상 시험 자료 + 파서 (지금의 묶음 A 1·2번이 여기로) | 스펙 3.3 규칙 15개 시험 통과, 화면 변경 0 |
| 2 | 나이테 | 팀원별 경험 저장(`people/<이름>/` 아래), 스키마 추가, 담당·회고에서 경험 초안 만들기 | 팀장 화면 하나에서 팀원 한 명의 경험 목록 |
| 3 | 나이테 | 구조화 왕복: STAR 정리 프롬프트의 응답을 **되받아** 파싱해 경험으로 (나이테는 지금 복사에서 끝난다) | 가상 응답 5종 |
| 4 | 나이테 | 역량 매핑, 정합성, 확정 상태 | |
| 5 | 나이테 | 팀원별 업무 이력 파일 내보내기, 팀원이 자기 것 보고 보완 | |

05 원안의 골격 복사(묶음 A-0)는 하지 않는다.

1단계를 느린 길 저장소에서 먼저 하는 방법(04 검토의 B안)도 있지만, 나이테 안의 따로 떨어진 폴더에서 해도 격리는 같고 저장소 두 개를 오가는 비용이 없다. 그래서 **1단계부터 나이테 안에서** 하는 쪽을 권한다.

## 6. ①이 나은 경우

아래 중 하나라도 맞으면 ①을 다시 본다.
- 느린 길을 나이테가 없는 다른 팀이나 개인에게도 따로 배포할 계획이 있다
- 경험 모델·구조화 화면을 팀이 쓰는 시스템과 떨어진 곳에서 한참 실험해 보고 싶다
- 나이테 운영 절차(배포본·체크리스트) 때문에 새 기능 개발 속도가 감당이 안 된다
