## 0. 검토 요약

### 전체 평가

컨셉 문서로서 완성도는 높다. 특히 다음 네 가지는 이후 문서의 기준으로 그대로 유지할 가치가 있다.

- "경력"이 아니라 "경험"을 기본 단위로 삼은 점 (4장)
- 원본 기록과 AI 생성 결과를 분리하는 원칙 (12장, 18장 Principle 3)
- AI를 "작성자가 아니라 정리자"로 정의한 점 (Principle 2)
- MVP에서 제외할 것을 명시한 점 (16장)

다만 이 문서는 "무엇을 만들 것인가"는 충분히 설명하지만, 02_REQUIREMENTS를 바로 쓰기에는 **결정되지 않은 전제**가 여러 개 남아 있다. 그 전제가 정해지지 않으면 요구사항, 데이터 모델, 기술 설계가 서로 다른 가정 위에서 작성될 위험이 있다.

### 핵심 결론 6가지

| # | 결론 | 영향 범위 |
|---|------|-----------|
| 1 | **콜드 스타트 문제가 다뤄지지 않았다.** 신규 사용자는 경험이 0개이므로 앱의 최종 가치(문서 생성)를 "몇 달 뒤"에야 확인할 수 있다. 과거 경력 일괄 등록 흐름이 필요하다. | 사용자 흐름, MVP 범위, 성공 기준 |

| 4 | **10년 자산을 목표로 하면서 백업·내보내기가 없다.** 로컬 저장만으로는 기기 분실 시 전부 사라진다. 백업과 데이터 내보내기는 MVP에 들어가야 한다. | MVP 범위, 기술 설계 |
| 5 | **문서 산출물이 PDF로 고정되어 있다.** 국내 채용 플랫폼(사람인, 잡코리아, 원티드 등)은 웹 폼 입력이 대부분이므로, 복사 가능한 텍스트 출력이 PDF보다 먼저일 수 있다. | 문서 생성 요구사항, PDF 설계 |

## A. 02_REQUIREMENTS 착수 전에 결정해야 할 사항 (Blocking)

아래 항목은 답이 달라지면 요구사항 문서의 상당 부분이 달라지므로, 02 작성 전에 결정하는 것을 권한다.

### A1. 콜드 스타트: 과거 경력 일괄 등록

**현재 문서의 공백**

- 13.1 최초 사용자 흐름은 "현재 직장/경력 입력 → 첫 번째 Experience 추가"로 끝난다.
- 23장 성공 기준 두 번째는 "몇 달 동안 기록한 경험을 바탕으로" 문서를 만들 수 있는가이다. 즉 가치 검증에 최소 수개월이 걸린다.
- 실제 사용자는 이미 5년, 10년의 경력을 갖고 시작한다. 그 경력을 앱에 넣을 방법이 없으면 "지금 당장 경력기술서가 필요한 사용자"는 앱을 쓸 이유가 없다.

**개선 방향**

- 온보딩에 **"과거 경력 불러오기"** 흐름을 추가한다.
  - 기존 경력기술서·이력서 텍스트(또는 PDF/DOCX)를 붙여 넣으면 AI가 Career / Project / Experience 후보로 분해한다.
  - 회사별로 "이 회사에서 기억나는 일을 자유롭게 말해 보세요" 식의 회고 인터뷰 모드를 제공한다.
- 이렇게 하면 성공 기준을 두 개로 나눌 수 있다.
  - 단기 기준: 첫 사용 30분 안에 기존 경력으로 경력기술서 초안을 만들 수 있는가
  - 장기 기준: 이후 꾸준히 기록한 경험이 다음 문서를 더 좋게 만드는가
- 이 기능은 AI 구조화 엔진을 그대로 재사용하므로 구현 비용 대비 활성화 효과가 가장 크다.

### A2. AI 처리 구조와 최소 백엔드의 정의

**현재 문서의 공백**

- 17장은 "외부 AI API로 전달되는 데이터를 명확히 표시"라고 하여 클라우드 AI를 전제한다.
- 16장은 "복잡한 클라우드 백엔드"를 제외한다.
- 17장은 "로컬 우선(Local-first) 구조를 고려"한다.
- 이 셋은 양립할 수 있지만, 그러려면 "복잡하지 않은 백엔드"가 무엇인지 정해야 한다. API 키를 앱에 내장하는 방식은 탈취 위험 때문에 선택지가 아니므로, 클라우드 AI를 쓰는 순간 최소한 인증과 요청 중계를 하는 서버가 필요하다.

**결정해야 할 질문**

1. AI 실행 위치: 온디바이스(Apple Foundation Models 등) / 클라우드 API / 혼합
   - 온디바이스: 개인정보 측면에서 가장 유리하고 비용이 0이지만, 한국어 구조화 품질과 지원 기기 범위가 제약이다.
   - 클라우드: 품질이 좋지만 비용, 키 관리, 개인정보 고지가 따라온다.
   - 혼합: 저장은 로컬, AI 요청만 클라우드. 가장 현실적이나 "최소 백엔드"가 필요하다.
2. 비용 부담 주체: 개발자 부담(구독 모델 필요) / 사용자 API 키 직접 입력(BYOK) / 무료 한도 + 유료
3. 오프라인 동작: 네트워크가 없을 때 기록은 가능해야 한다. "기록은 즉시 저장, 구조화는 나중에" 큐 구조가 필요한지 결정한다.
4. AI 제공자의 데이터 보존 정책: 학습에 사용되지 않는 옵션(zero data retention)을 요구사항에 포함할지 결정한다.

**개선 방향**

- 16장의 "복잡한 클라우드 백엔드 제외"를 다음과 같이 구체화한다.
  - 포함: AI 요청 중계, 익명 사용량 제한, 크래시 리포트 정도의 **얇은 서버**
  - 제외: 사용자 데이터 서버 저장, 계정 시스템(초기), 소셜/공유
- 사용자 데이터는 기기와 사용자의 iCloud에만 존재하고, 서버는 AI 요청을 통과시킬 뿐 저장하지 않는다는 원칙을 17장에 명시한다.

### A3. 데이터 모델: Entry 계층 추가와 중복 정리

**현재 문서의 공백**

1. **"기록"과 "경험"의 구분이 없다.**
   - 13.2 평상시 흐름은 "이번 달 팀 과제 진행 상황을 정리했다" 같은 한 줄 기록이다.
   - 이런 기록은 매달 반복된다. 매번 새 Experience를 만들면 같은 경험이 12개로 쪼개지고, 하나로 합치면 "언제 무엇을 했는지"의 원본이 사라진다.
   - 진행 중인 업무(시작했지만 끝나지 않은 프로젝트)를 어떻게 표현하는지도 정의가 없다.
2. **Experience와 Career가 같은 필드를 갖는다.**
   - 5장 Experience에 Period / Organization / Position이 있고, 8장 Career에도 Organization / Position / Period가 있다.
   - 어느 쪽이 원본이고 어느 쪽이 파생인지 정해야 한다.
3. **Achievement의 위치가 두 곳이다.**
   - 5장에서는 Experience 안의 Result로, 8장에서는 Profile 아래 독립 항목으로 나온다.
4. **Project가 MVP에 있는지 없는지 불명확하다.**
   - 8장은 "MVP는 Experience 중심"이라 하고, 9장은 Project → Experience 구조를 정의한다.
5. **역량(Skill)의 정규화 전략이 없다.**
   - 7.2 예시에서 AI가 "과제 관리"와 "프로젝트 관리"를 별개 역량으로 뽑는다. 이렇게 자유 텍스트로 쌓이면 Home의 "주요 역량"과 Experience List의 역량 필터가 의미를 잃는다.

**개선 방향**

- 3계층 모델로 정리하는 것을 제안한다.

```text
Career (회사/직위/기간)           ← 사용자가 직접 관리, 소수
  └── Project (과제, 선택 사항)    ← 없어도 됨, 나중에 묶기 가능
        └── Experience (구조화된 경험)  ← AI + 사용자 확정, 문서의 재료
              └── Entry (원본 기록)     ← 날짜 + 원문(텍스트/음성 전사), 수정 불가
```

- Entry는 원본 보존(Principle 3)의 실체가 된다. 하나의 Experience에 여러 Entry가 붙을 수 있고, 한 Entry에서 여러 Experience 후보가 나올 수도 있다.
- Experience의 Organization / Position은 Career를 참조해 상속하고, 필요할 때만 덮어쓴다.
- Achievement는 MVP에서 독립 엔티티로 만들지 않고 Experience.Result로 둔다. 8장의 Achievements는 "성과 기준으로 Experience를 조회하는 뷰"로 재정의한다.
- Project는 MVP에서 "선택적 태그"로 시작한다. Experience 생성 시 Project 지정을 강제하지 않는다.
- Skill은 **앱이 제공하는 기본 역량 사전 + 사용자 추가 항목 + 동의어 병합** 구조로 한다. AI는 자유 텍스트를 뽑되, 저장 시 사전의 표준 항목에 매핑하고, 매핑되지 않은 항목은 사용자가 확인한다.
- Experience에 **상태**를 둔다: `초안(Entry만 있음)` → `구조화됨(AI 처리)` → `확정(사용자 검토)` → 이후 문서 사용 가능. 문서 생성 시 확정된 경험만 재료로 쓰면 12장 원칙을 지키기 쉬워진다.

### A4. 백업, 동기화, 내보내기

**현재 문서의 공백**

- Principle 4는 "1년, 5년, 10년 동안 축적"을 목표로 한다.
- MVP 저장은 "로컬 데이터 저장"만 있다. 기기 분실, 교체, 앱 삭제 시 데이터가 전부 사라진다.
- 데이터 내보내기가 어디에도 없다. 커리어 데이터는 사용자의 것이므로 언제든 가져갈 수 있어야 한다는 것은 17장 개인정보 원칙과도 맞닿는다.

**개선 방향**

- MVP에 다음을 포함한다.
  - iCloud 동기화(CloudKit). 개인 기기 간 동기화이므로 "복잡한 클라우드 백엔드"에 해당하지 않으며 로컬 우선 원칙과도 맞는다.
  - 전체 데이터 내보내기(JSON + Markdown). 사용자 신뢰 장치이자 향후 마이그레이션 안전장치다.
  - 전체 데이터 가져오기(복원).
- 10년 사용을 전제로 하므로 **스키마 버전 관리와 마이그레이션 정책**을 04_DATA_MODEL의 필수 항목으로 넣는다.

### A5. 타깃 사용자 확정

**현재 문서의 공백**

- 2장은 "직장인"을 대상으로 하지만, 유일한 예시(7.2, 9장)는 제조업 팀장(스마트팩토리 AI 과제, 경영층 보고)이다.
- 개발자, 사무직 실무자, 관리자, 전문직은 경력기술서 형식·역량 어휘·기록 습관이 모두 다르다. 이 결정이 역량 사전, 문서 템플릿, 후속 질문의 톤을 결정한다.

**개선 방향**

- 1차 페르소나 1개, 2차 페르소나 1~2개를 정한다. 예: 1차 "10년차 이상 관리자급 직장인, 이직·평가 준비", 2차 "3~7년차 실무자".
- 페르소나별로 "경력기술서를 쓰는 상황"을 시나리오로 적는다(이직, 사내 평가, 승진, 프리랜서 제안서 등). 이 시나리오가 02의 사용자 시나리오 항목이 된다.

### A6. MVP 단계 재분할

**현재 문서의 공백**

- 15장 MVP에는 기본 CRUD, 음성 입력, 메모 가져오기, AI 구조화, 후속 질문, 역량 추출, 성과 추출, 문서 데이터 선택, 문서 생성, PDF 출력이 모두 들어 있다.
- 15장의 첫 문장 "기능을 욕심내지 않는다"와 어긋난다.

**개선 방향**

| 단계 | 목표 | 포함 |
|------|------|------|
| MVP-0 (검증) | "1~2분 안에 기록할 수 있는가" 검증 | 텍스트 기록, AI 구조화, 후속 질문(지연형), Experience 목록/상세/수정, 과거 경력 불러오기(텍스트 붙여 넣기), iCloud 백업, 데이터 내보내기 |
| MVP-1 (가치) | "실제로 쓸 수 있는 경력기술서가 나오는가" 검증 | 경험 선택, 경력기술서 생성, 텍스트 복사, PDF 출력 |
| MVP-2 (편의) | 기록 마찰 감소 | 음성 입력, 공유 확장(Share Extension)으로 메모 가져오기, 리마인더 |

- 음성 입력과 메모 가져오기는 핵심 가설(경험 → 구조화 → 문서) 검증에 필수가 아니므로 뒤로 미루는 것을 권한다.

## B. 02_REQUIREMENTS에서 구체화해야 할 사항

A의 결정이 끝난 뒤, 02에서 요구사항으로 풀어야 할 항목이다.

### B1. 기록 흐름의 세부 규칙

- **후속 질문 시점.** 7.1은 입력 직후 질문하는 흐름이고, 13.2는 "나중에 보완 질문"이다. 둘 다 가능하지만 기본값을 정해야 한다. 성공 기준(1~2분 기록)을 지키려면 **기본은 지연형**(저장 먼저, 질문은 나중에)이 맞다.
- **질문 개수 상한과 건너뛰기.** 7.2 예시는 질문이 5개다. 최대 개수, "모름/해당 없음" 선택, 질문 무시 시 재노출 규칙을 정한다.
- **미답변 질문의 위치.** Home에 "보완 대기 3건"처럼 노출할지, Experience 상세에서만 볼지 정한다.
- **유도 질문 경계.** "과제 관리 시간이 줄었습니까?"는 성과를 유도하는 질문이다. 12장 원칙(존재하지 않는 성과 생성 금지)과 충돌하지 않도록, 질문은 열어 두고("달라진 점이 있었다면 무엇입니까?") "없음"이 정상 답변이 되게 하는 원칙을 넣는다.
- **AI 재구조화와 사용자 수정의 충돌.** 사용자가 수정한 Experience에 새 Entry가 추가되어 AI가 다시 구조화할 때 사용자 수정을 덮어쓰지 않는 규칙이 필요하다.

### B2. 반복 경험과 진행 중 경험

- 월 단위로 반복되는 업무(정기 보고, 팀 관리)를 하나의 Experience에 Entry로 누적하는 규칙
- 새 Entry가 들어왔을 때 "기존 Experience에 추가 / 새 Experience 생성"을 AI가 제안하고 사용자가 고르는 흐름
- 기간이 "진행 중"인 Experience의 표현과, 종료 시 정리(회고) 유도

### B3. 문서 생성 요구사항 (경력기술서)

- **국내 경력기술서 형식.** 회사 역순 → 프로젝트 → 기간/역할/주요 업무/성과가 일반적이다. 기본 템플릿 1개를 정하고, 문체(개조식 vs 서술형), 분량 상한(보통 A4 2~3장)을 요구사항으로 적는다.
- **목표 지향 생성.** "사용할 경험 선택"만 있고, 어떤 회사·직무에 낼 것인지 입력이 없다. 채용공고(JD) 텍스트를 붙여 넣으면 관련 경험을 추천하고 강조점을 조정하는 기능은 "채용공고 자동 매칭"(16장 제외 항목)과 다르며 MVP-1 범위에서 검토할 가치가 있다.
- **출력 형식 우선순위.** 국내 채용 플랫폼은 웹 폼 입력이 대부분이므로 **섹션별 복사 가능한 텍스트**를 PDF와 동등하거나 그 이상으로 다룬다. PDF만으로는 실제 지원 흐름에서 쓰기 어렵다.
- **문서 편집과 버전.** 생성 후 앱 안에서 수정하는지, 수정 후 재생성 시 사용자 수정이 유지되는지, 문서를 여러 버전 저장하는지 정한다.
- **경험 변경의 전파.** 문서 생성 후 원본 Experience가 바뀌면 문서를 갱신하는지, 스냅샷으로 남기는지 정한다. 12장 6번(원본과 문서 분리)에 따르면 스냅샷이 맞다.
- **회사명 익명화 옵션.** 재직 중 이직 준비 등 "국내 대기업 제조사"처럼 표현해야 하는 경우가 있다.

### B4. 원칙 12(과장 금지)의 실행 방안

원칙은 명확하지만 어떻게 강제할지가 없다. 다음을 요구사항으로 옮기는 것을 제안한다.

- 생성된 문서의 모든 문장은 **출처 Experience를 참조**한다. UI에서 문장을 누르면 원본 경험을 볼 수 있다.
- 문서에 등장하는 **모든 숫자는 Experience의 정량 성과 필드에 존재해야 한다.** 존재하지 않으면 생성 결과에서 제거하거나 "확인 필요" 표시를 한다.
- 문서 초안에는 AI가 추정한 부분을 시각적으로 구분한다(예: 밑줄 또는 색상).
- 확정(사용자 검토) 상태가 아닌 Experience는 문서 재료로 쓰지 않는다.

### B5. 개인정보와 민감정보

- **AI로 전송되는 필드의 범위 정의.** Evidence(문서, 이미지)는 전송하지 않는다 등 필드별 규칙.
- **전송 전 익명화 옵션.** 회사명, 인명, 제품명을 자동 치환한 뒤 전송하고, 결과에서 복원하는 기능. 17장 "민감한 회사 정보 입력 주의사항"을 경고문에서 기능으로 격상시킬 수 있다.
- **AI 끄기 모드.** AI를 전혀 쓰지 않고 수동으로만 기록하는 모드가 필요한지 결정한다. 보안이 엄격한 직장의 사용자에게 필요할 수 있다.
- **법적 사항.** 개인정보 처리방침, App Store 개인정보 라벨, AI 제공자 데이터 처리 조건을 비기능 요구사항에 포함한다.
- **Evidence 저장 정책.** 이미지·문서 첨부의 용량 제한, iCloud 동기화 포함 여부.

### B6. 습관 형성과 재방문

- 기록 앱의 최대 위험은 이탈이다. 문서에 재방문 장치가 전혀 없다.
- 최소 요구사항: 주기 리마인더(요일·시간 설정), 주간 회고 프롬프트("이번 주에 한 일 중 남길 것이 있나요?"), 기록 공백 알림.
- 선택 검토: 캘린더 읽기 권한을 받아 "지난주 회의 X에서 무엇을 했나요?" 같은 맥락형 프롬프트. 마찰을 크게 줄이지만 권한 요청 부담이 있다.
- 23장 성공 기준에 **재방문 지표**(주간 기록 사용자 비율, 4주 후 잔존율)를 추가한다.

### B7. 화면 요구사항 보완 (14장)

- Experience List에 **검색**(전문 검색)이 없다. 필터보다 먼저 필요하다.
- **삭제와 복구.** 10년 자산이므로 휴지통 또는 삭제 취소가 필요하다.
- **AI Review 화면의 상호작용.** 필드별 수락/거절, 재생성, 원문 대조 보기, 되돌리기 중 무엇을 제공할지.
- Home의 "주요 역량"은 역량 정규화(A3) 없이는 구현할 수 없다. 의존 관계를 명시한다.
- **빈 상태(Empty State) 설계.** 경험 0개, 문서 0개일 때의 화면이 콜드 스타트(A1) 흐름의 진입점이다.

### B8. 음성 입력과 메모 가져오기의 현실성

- 음성: 온디바이스 음성 인식(iOS 기본) vs 클라우드 전사. 한국어 인식 품질, 녹음 길이 상한, 원본 오디오 보존 여부.
- 메모 가져오기: Apple 메모 앱은 외부 API가 없다. 현실적인 경로는 **공유 확장(Share Extension)**과 클립보드 붙여 넣기다. "메모를 가져온다"는 표현을 이 두 방식으로 구체화해야 한다.

### B9. 비기능 요구사항

문서에 전혀 없는 항목이다. 02의 비기능 요구사항 절에 최소 다음을 넣는다.

- 지원 플랫폼과 최소 OS 버전 (iPhone 전용인지, iPad·Mac 확장 계획)
- 오프라인 동작 범위
- AI 응답 시간 목표와 실패 시 동작(재시도, 수동 입력 대체)
- AI 비용 상한(사용자당 월 예산) 또는 사용량 제한 정책
- 접근성(Dynamic Type, VoiceOver), 다크 모드
- 언어: MVP는 한국어 전용인지, UI 영문화 시점
- 데이터 마이그레이션과 하위 호환

### B10. 비즈니스 모델

- 무료·구독·일회 구매 중 무엇인지 언급이 없다. 클라우드 AI를 쓰면 사용자당 변동 비용이 생기므로 A2와 함께 결정해야 한다.
- 구독이라면 "구독 해지 후 데이터 접근성"을 명시해야 한다. 기록은 남고 AI만 멈추는 방식이 Principle 4와 부합한다.

## F. 추가 검토: AI 처리 방식 (앱 내 AI vs 프롬프트 내보내기)

> 배경: 사용자가 생각나는 대로 입력한 내용은 생성형 AI로 계속 보정해야 하는데, 외부 API 비용이 부담되므로 "앱은 이력을 잘 구조화해 프롬프트로 변환하고, 사용자가 본인의 생성형 AI에 복사해 쓰는 방식"이 검토되었다.

### F1. 결론

- **기록·구조화 단계는 앱 안의 AI로, 문서 다듬기 단계는 사용자의 AI로** 나누는 것을 권한다.
- 프롬프트 내보내기 아이디어는 버릴 것이 아니라 **적용 위치를 바꿀 것**이다. "활용" 단계에는 잘 맞고, "기록" 단계에는 맞지 않는다.
- 비용은 이 결정의 핵심 변수가 아니다. 구조화 1회 비용은 원화로 10원 안팎이며, 진짜 문제는 (1) 무료 사용자의 무제한 사용, (2) API 키를 안전하게 쓰기 위한 얇은 서버, (3) 비용을 회수할 수익 모델 부재다.

### F2. 비용 추정 (공개 단가 기준, 한국어 토큰 효율 감안한 보수적 가정)

| 작업 | 토큰 가정 | 소형 모델 | 중형 모델 |
|------|-----------|-----------|-----------|
| 경험 구조화 1회 | 입력 2,000 / 출력 800 | 약 $0.006 | 약 $0.012 |
| 경력기술서 생성 1회 | 입력 15,000 / 출력 4,000 | 약 $0.035 | 약 $0.07 |
| 헤비 유저 월간 (기록 20건 × 2회 호출 + 문서 5회 재생성) | | 약 $0.4 | 약 $0.85 |

- 헤비 유저 기준으로도 월 1,200원 안팎이다. 일반 사용자는 이 1/4 수준이다.
- 시스템 프롬프트를 캐싱하면 입력 비용이 더 내려간다. "나중에 보완"처럼 즉시성이 필요 없는 구조화는 배치 처리로 절반 가격에 돌릴 수도 있다.
- 결론: 월 3,000~5,000원 구독이면 AI 비용을 충분히 회수한다. 무료 사용자에게는 월 N회 할당량을 두면 손실이 상한된다.

### F3. 프롬프트 내보내기를 "기록" 단계에 쓸 때의 문제

1. **핵심 루프가 끊어진다.** 앱의 가치는 "기록 → 구조화 → 축적"인데, 구조화가 앱 밖에서 일어나면 결과를 다시 앱에 가져와 필드에 나눠 붙여야 한다. 경험 1건당 앱 전환 2회, 붙여넣기 여러 번이 생겨 "1~2분 기록" 기준이 무너진다.
2. **결과를 다시 데이터로 만들 수 없다.** 외부 AI 응답은 자유 텍스트다. JSON으로 달라고 요청하고 앱이 파싱하는 방법은 가능하지만, 비개발자 사용자에게 매우 낯설고 실패율이 높다.
3. **후속 질문 흐름(7.1)이 불가능하다.** "관리한 과제는 몇 개였습니까?" 같은 보완 질문과 답변 수집은 앱이 대화를 통제할 때만 된다.
4. **과장 금지 원칙(12장)을 강제할 수 없다.** 외부 AI는 성과를 자연스럽게 부풀린다. 출처 추적, 수치 검증 같은 장치가 모두 앱 밖에 있게 된다.
5. **개인정보 이점이 생각보다 작다.** 데이터는 어차피 제3자 AI로 간다. "사용자가 직접 선택했다"는 차이는 있지만 보호 수준이 높아지는 것은 아니다.
6. **재방문 이유가 사라진다.** 앱이 "양식 + 프롬프트 생성기"가 되면 이직 시기에만 여는 앱이 되어 Principle 4(시간이 지날수록 가치 증가)와 어긋난다.

### F4. 프롬프트 내보내기가 "활용" 단계에 잘 맞는 이유

- 이직 준비 중 사용자는 이미 ChatGPT, Claude 등에서 몇 시간씩 문서를 다듬는다. 이 반복 작업은 취향과 목표 회사에 따라 달라지고, 채팅 UI가 가장 편하다. 앱이 이 경험을 대체하려 하면 비용은 늘고 만족도는 낮다.
- 반면 사용자가 자기 AI에 붙여 넣을 **재료**는 앱만 만들 수 있다. 확정된 경험 데이터, 정량 성과, 역량 태그, 과장 금지 지시문, 목표 문서 형식을 하나의 프롬프트로 묶어 주면 사용자가 얻는 결과 품질이 크게 올라간다.
- 사용자가 관찰한 "계속 보정해야 한다"는 문제는 두 종류로 나뉜다.
  - **사실 보완**: 빠진 수치, 맥락, 기간. 짧은 질의응답이며 앱 안에서 저렴하게 처리해야 한다. 이것이 데이터 자산이 된다.
  - **표현 다듬기**: 문체, 강조점, 회사 맞춤. 반복적이고 취향 의존적이다. 사용자의 AI에 넘기는 것이 맞다.
- 이 분리는 Principle 2("AI는 작성자가 아니라 정리자")와 정확히 맞는다. 앱의 AI는 사실을 정리하고, 문장을 꾸미는 일은 사용자와 사용자의 AI가 한다.

### F5. 제안 구조

```text
[기록 단계]  앱 내 AI (소형 모델 + 구조화 출력 + 프롬프트 캐싱)
  텍스트 입력 → 구조화 → 후속 질문 → 확정 → Career Data

[활용 단계]  세 가지 출구
  1) 앱 내 초안 생성        : 경력기술서 1회 생성 + 텍스트 복사 + PDF
  2) 프롬프트 내보내기       : 선택한 경험 + 원칙 + 형식을 프롬프트로 묶어 클립보드/공유
  3) 커리어 컨텍스트 파일    : 전체 Career Data를 Markdown으로 내보내 사용자의 AI에
                             참고 문서로 첨부 (ChatGPT/Claude의 프로젝트 기능 등)
```

- 2)와 3)은 서버 비용이 0이고 구현이 가장 쉽다. MVP-1에 넣어 사용자가 앱 내 생성과 내보내기 중 무엇을 더 쓰는지 측정한다.
- 3)은 "느린 길이 만든 커리어 데이터 파일을 내 AI에 넣으면 어떤 문서든 만들 수 있다"는 메시지가 되어, 문서 종류를 앱이 다 구현하지 않아도 11.2의 향후 확장 목록을 상당 부분 대체한다.

### F6. 기록 단계 비용을 더 낮추는 선택지

| 선택지 | 장점 | 단점 |
|--------|------|------|
| 온디바이스 모델(Apple Foundation Models) 1차 처리, 클라우드는 보완 | 비용 0, 개인정보 최선, 오프라인 가능 | 지원 기기 제한, 한국어 구조화 품질 검증 필요 |
| 소형 클라우드 모델 + 구조화 출력 | 품질 안정, 구현 단순 | 얇은 중계 서버 필요, 사용량 제한 필요 |
| 사용자 API 키 입력(BYOK) | 개발자 비용 0 | ChatGPT 구독자는 API 키가 없다. 개발자 등 소수에게만 유효. 보조 옵션으로만 |
| 무료 할당량 + 구독 | 손실 상한, 수익 모델과 일치 | 결제 구현, 해지 후 정책 필요 |

권장 조합: **소형 클라우드 모델 + 무료 할당량 + 구독**을 기본으로 하고, BYOK는 설정 메뉴의 보조 옵션으로 둔다. 온디바이스 모델은 지원 기기에서 한국어 품질을 검증한 뒤 1차 처리기로 승격을 검토한다.

### F7. 이 결정이 바꾸는 요구사항

- 15장 MVP 문서 항목에 "프롬프트 내보내기"와 "커리어 컨텍스트 파일 내보내기"를 추가한다.
- 12장 과장 금지 원칙의 실행 장치(B4)는 앱 내 생성에만 적용되고, 내보내기에는 **프롬프트 안의 지시문**으로 포함한다. 사용자의 AI가 이를 지킬지는 보장할 수 없음을 문서에 명시한다.
- 23장 성공 기준에 "확정된 경험을 재료로 사용자가 어떤 출구를 택했는가"를 측정 항목으로 넣는다.
- 결정 체크리스트(E)의 "AI 실행 위치"와 "비용 부담" 항목의 권장 답은 이 절을 따른다.
