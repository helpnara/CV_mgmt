## 2. 연동의 원칙 (제안)

1. **한 방향**: 느린 나이테 → 느린 길. 느린 길이 느린 나이테의 형식을 알고, 느린 나이테는 느린 길을 모른다. 사내 시스템에 개인 커리어 도구의 흔적을 남기지 않는다(238 ④와 같은 이유).
2. **사람이 옮긴다**: 네트워크·공유 폴더·API 연결은 없다. 사용자가 사내에서 복사하거나 파일로 받아, 회사 규정이 허용하는 범위에서 개인 PC로 옮긴다. 느린 길 NFR-03(외부 요청 0), D-008(프롬프트 왕복)과 같은 방식이다. 옮기는 행위의 책임은 사용자에게 있다(D-009와 같은 구조).
3. **사내 사실의 원천은 느린 나이테, 개인 자산화는 느린 길**: 과제·일지·담당·회고는 느린 나이테에서 쓰고, 느린 길은 그것을 받아 경험으로 다듬고 회사를 넘어 쌓는다. 같은 사실을 두 곳에서 따로 쓰게 하지 않는다.
4. **가져올 때 빼는 것**: 다른 사람 이름, 효과 금액, 면담 기록. 느린 나이테의 복사·프롬프트가 이미 빼고 있는 것과 같다.
5. **코드는 형제**: 같은 골격에서 출발하고, 같은 파일은 같게 유지해 나중에 공통 코어로 묶을 수 있게 한다(05 §9).

## 3. 연동의 세 층

### 3.1 코드 층: 형제 구조로 시작

| 할 일 | 언제 | 비용 |
|-------|------|------|
| 골격 복사 시 **출처 표** `docs/SKELETON.md`: 파일마다 느린 나이테 원본 경로, 출처 커밋(`a23bd75`), 구분(그대로 / 고침), 고친 이유 | 묶음 A-0 | 작음 |
| "그대로 복사" 파일은 **내용을 고치지 않는다.** 이름·환경 변수·포트처럼 다른 값은 `config.py` 상수와 환경 변수로 몰아, 원본과 `diff`했을 때 차이가 0이 되게 한다 | 묶음 A-0 | 작음. 05 §2.1의 "교체할 것"을 파일 안이 아니라 설정으로 옮기는 정도 |
| 느린 나이테에서 고친 결함을 받아 올 때 출처 표로 해당 파일을 찾고 커밋을 갱신한다 | 수시 | |
| 공통 코어 패키지 분리 | M1 뒤 (05 §9 그대로) | |

출처 커밋은 `a23bd75`를 유지한다. 그 뒤 커밋(244~247)은 운영 서버·관리자 분리 등 1인 도구에 필요 없는 변화가 대부분이다. 공통 파일 중 결함 수정이 있으면 골라 받는다.

### 3.2 데이터 층: 느린 나이테 이력을 느린 길로 가져오기

| 안 | 방식 | 느린 나이테 변경 | 판단 |
|----|------|------------------|------|
| **D-1. 복사 텍스트를 기록으로** | 사람별 이력의 [글로 복사]·[한 해 글로 복사] 결과를 느린 길에 `기록(종류: 업무 이력)`으로 붙여 넣는다. 이후는 경력기술서 분해(FR-D)와 같은 길: 분해 프롬프트 → AI → 응답 붙여넣기 → 파서 → `구조화` 경험 | **없음** | **M0 권장.** 기록 종류 하나와 분해 프롬프트 안내 문구만 늘어난다 |
| D-2. 느린 나이테 STAR 프롬프트 출력을 `slow-way` 블록으로 | 느린 나이테 프롬프트에 블록 형식을 넣어 AI 응답을 곧바로 느린 길 파서로 | 있음 (사내 프롬프트에 개인 도구 형식) | **비권장.** 원칙 1 위반, 사내 평가용 출력과 섞인다 |
| D-3. 기계가 읽는 이력 파일 | 느린 나이테에 중립적인 "업무 이력 파일로 받기"(md, `키: 값` 줄)를 하나 두고, 느린 길이 AI 없이 그대로 읽어 `초안` 경험을 만든다. 과제 번호로 다시 가져와도 중복이 생기지 않는다 | 있음 (작은 내보내기 하나, 용어는 중립) | **M1 후보.** D-1을 써 보고 숫자 손실·중복이 문제일 때 |
| D-4. 실시간 연결 | API, 공유 폴더, 같은 vault | 큼 | **제외.** 다른 PC·사내망, NFR-03 위반 |

**D-1을 M0에 넣는 이유**
- 느린 나이테 쪽 변경이 0이라 사내 시스템에 영향이 없다.
- 분해 프롬프트·파서·확정 화면을 그대로 쓴다. 실험 01에서 경력기술서 분해가 검증된 경로다.
- 1차 페르소나(개발자 본인)는 경력기술서와 느린 나이테 이력을 둘 다 갖고 있다. S1(콜드 스타트)에서 경력기술서로 과거를, 느린 나이테 이력으로 최근을 채우는 것이 자연스럽다.
- `02_PLATFORM_REVIEW.md` §3의 기록 빈틈(근무 중 기록 불가)을 상당 부분 메운다. 근무 중 기록은 느린 나이테 일지·회고로 이미 하고 있으니, 느린 길은 그것을 주기적으로 받으면 된다.

### 3.3 개념 층: 필드 대응

느린 길 용어(D-012)와 느린 나이테 용어는 "과제"가 같은 뜻이라 대응이 쉽다.

| 느린 나이테 | 느린 길 | 비고 |
|-------------|---------|------|
| 과제(번호·과제명) | Project(과제) | 과제 번호를 출처로 남기면 다시 가져올 때 같은 과제로 묶인다 |
| 과제 개요의 배경·목표 | Experience 상황·목표 | STAR 정리 프롬프트(244)가 이미 이 대응을 쓴다 |
| 담당 기간(시작~끝) | Experience 기간 | 과제 기간이 아니라 **본인 담당 기간** |
| 역할(주관·참여·지원) + 맡은 부분 | Experience 역할 | R-07(본인 몫과 다른 주체 구분)과 잘 맞는다 |
| 내가 한 일 | 행동 | |
| 결과, 그 밖의 성과, 중간 성과 | 결과_정성, 결과_정량 | 숫자는 기준을 모르면 "기준 없음" + 확인 필요 |
| 기술·도구 | 역량_기술 | |
| `★성과` 일지 | 기록(Entry) 후보 | M1 |
| 교육·행사(교육·세미나·학회·자격) | 증빙 또는 프로필 | 자격·인증은 프로필, 나머지는 M1에서 판단 |
| 효과 금액, 다른 사람 이름, 면담 | 가져오지 않음 | 원칙 4 |

## 6. 결론을 바꿀 수 있는 사실 (개발자 확인 필요)

| 질문 | 답에 따른 변화 |
|------|----------------|
| 회사 규정상 느린 나이테의 본인 이력 텍스트를 개인 PC로 옮겨도 되나 | **안 되면** 데이터 층(3.2)은 접고 코드 층(3.1)만 남긴다. 가장 먼저 확인할 것 |
| 느린 나이테 쪽을 고칠 의향이 있나 (D-3) | 없으면 D-1로 계속 간다. 있으면 별도 저장소 작업이며 이 세션에 그 저장소를 붙여야 한다 |
| 느린 나이테를 쓰는 팀원에게 느린 길을 권할 생각이 있나 | 있으면 M1 베타 후보가 생긴다. 다만 팀장이 팀원에게 개인 커리어 도구를 권하는 모양이 사내에서 어떻게 보일지(238 ④와 같은 결) 먼저 판단 |
| 연동이 코드 공유를 넘어 "한 앱"을 뜻했나 | 그렇다면 느린 나이테 안에 개인 영역을 두는 안이 되는데, 사내 서버에 개인 커리어 자산을 두는 것이라 D-009와 정면으로 부딪친다. 권하지 않는다 |
