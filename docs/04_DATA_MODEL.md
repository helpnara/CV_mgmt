## 1. 용어 (D-012)

| 영문 | 한국어 | 뜻 | ID |
|------|--------|----|----|
| Career | 경력 | 회사·조직·직위·기간. 이력서의 "경력 사항" 한 줄 | `C-nn` |

## 2. 계층과 관계

```text
Career (경력, 필수)
 └─ Project (과제, 선택)
     └─ Experience (경험)  ←─ Entry (기록) 0..n
          ├─ Quant 0..n
          ├─ Evidence 0..n
          ├─ Skill 태그 0..n  (역량 사전 참조)
          └─ 관련 경험 0..n   (E-009 → E-002 같은 횡단 참조)
```

- 경험은 경력 하나에 속한다. 두 경력에 걸치면(실데이터 E-002, E-018) **주 경력 하나**를 정하고 "관련 경력"에 나머지를 적는다. 컨텍스트 파일의 경력 역순 묶음이 이 주 경력을 따른다.
- 과제는 선택이다. 과제 없이 경력 바로 아래 경험이 있을 수 있다.
- 기록은 경험에 0..n개 붙는다. 기록 하나가 경험 여러 개의 재료가 될 수도 있다(경력기술서 분해). 기록은 절대 수정·삭제하지 않고, 경험이 삭제돼도 남는다(01 문서 Principle 3).
- 경험 간 참조는 방향이 있다(E-009가 E-002를 참조). 역참조는 색인이 계산한다.

|------|----|------|------|
| metric | 문자열 | ✓ | 지표. "오탐지율" |

| baseline | 문자열 | ✓ | 비교 기준. 없으면 리터럴 `기준 없음` |
| when | 문자열 | | 시점. "2019", "2022 대비 2024" |

`baseline_kind`가 `비교`일 때만 컨텍스트 파일에서 비교 표현이 허용된다. 나머지는 "기준 없음" 규칙을 적용한다. 실데이터 19개 중 비교 5, 집계 14였다.

## 4. 경험 상태 머신

```text
초안 ──(구조화 응답 파싱·사용자 저장)──▶ 구조화 ──(사용자 확정)──▶ 확정
 ▲                                          │                         │
 └──────────(사용자가 되돌림)────────────────┴─────────────────────────┘
```

| 상태 | 뜻 | 들어오는 길 | 컨텍스트 파일 기본 포함 |
|------|----|-------------|------------------------|
| 초안 | 제목만 있거나 사용자가 직접 쓰다 만 것 | 수동 생성, 파싱 실패 | 아니오 |
| 구조화 | AI 응답을 파싱해 필드가 채워졌으나 사용자가 검토하지 않음 | 파서, 분해 | 아니오 (옵션으로 포함 가능) |
| 확정 | 사용자가 검토해 사실로 인정함 | 확정 버튼 | **예** |

**확정 조건** (모두 만족해야 버튼이 활성화된다)
1. `title`, `career`, `role`, `kind`가 채워져 있다.
2. `situation`·`actions`·(`quants` 또는 `result_qual`) 중 둘 이상이 채워져 있다. 이름만 있는 빈 경험(실데이터 E-008 같은 것)은 확정할 수 없다.
3. `open_questions`가 비어 있다. 질문이 남아 있으면 "답하거나 지운다".
4. 모든 `quants`의 `baseline_kind`가 `미확인`이 아니다.
5. 정합성 검사(8절)에 경고가 없거나, 사용자가 각 경고를 "확인함"으로 넘겼다.

확정 뒤에 필드를 고치면 상태는 유지되고 `updated`만 바뀐다. 기간·경력을 바꾸면 정합성 검사를 다시 돌린다.

## 5. ID 체계

- `C-nn`, `P-nn`, `E-nnn`, `N-nnnn`. 접두어 + 0 채움 숫자. 생성 순서로 1씩 증가하고 **재사용하지 않는다**. 삭제된 번호는 비어 있는 채로 둔다.
- 번호는 vault 전체에서 유일하다. 파일명이 ID를 담는다(6절).
- 컨텍스트 파일의 근거 ID `(E-nnn)`가 10년 뒤에도 같은 경험을 가리켜야 하므로 ID는 불변이다. 경험을 둘로 나누면 원본은 그대로 두고 새 ID를 발급한다. 둘을 합치면 하나를 남기고 다른 하나는 `merged_into`를 적고 보관한다.
- 자리수가 넘치면(경험 1,000건) 자리수만 늘린다. 정렬은 숫자로 한다.

## 6. 파일 형식 (vault)

D-006·D-009에 따라 원본은 `vault/` 안의 Markdown + front matter다. 느린 나이테와 같은 구조(`docs/reference/neurin-naite-profile.md` 4절).

```text
vault/
├── careers/        C-01.md …
├── projects/       P-01.md …
├── experiences/    E-001.md …
├── entries/        2026/N-0001.md …   (연도 폴더)
├── attachments/    E-001/ … , N-0001/ …
├── skills.yaml     역량 사전 (기본 사전 + 사용자 추가)
├── profile.md      이름·학력·자격·기술 (경험이 아닌 것)
└── .index/         SQLite 파생 색인 (삭제 가능)
```

schema: 1

## 상황
…

## 목표
…

## 행동
- …

## 결과
- 정성: …
- 비즈니스 영향: …

- front matter에는 **짧고 구조적인 값**만 둔다. 긴 본문(상황·목표·행동·결과·교훈·확인 필요)은 본문 절로 둔다. Obsidian·VS Code에서 그대로 읽고 고칠 수 있어야 한다(느린 나이테 원칙).
- `quants`·`evidences`·`skills`는 front matter의 flow 매핑으로 둔다. 한국어 값에 콜론·따옴표가 있으면 따옴표로 감싼다. **쓰기는 앱이 하고, 읽기는 관용 로더**(느린 나이테 `markdown.py`)로 한다.
- 본문 절 제목은 고정이다(상황/목표/행동/결과/교훈/확인 필요). 색인기는 제목으로 절을 찾는다. 없는 절은 빈 값.
- 컨텍스트 파일 내보내기는 이 파일들을 읽어 `docs/spec/context_file.md` 2절 형식으로 합친다. 역방향(컨텍스트 파일 → vault)은 만들지 않는다.

## 8. 정합성 검사 (R-04, 스펙 5절)

색인기가 vault를 읽을 때와 사용자가 경험을 저장할 때 돌린다. 결과는 경고 목록이며 저장을 막지 않는다. 확정만 막는다(4절 조건 5).

| 코드 | 검사 | 예 |

## 10. 스키마 버전과 마이그레이션

- 모든 vault 파일의 front matter에 `schema: N`. 현재 1.
- 앱은 자기 스키마 버전보다 낮은 파일을 읽으면 **읽을 때 변환**하고, 사용자가 저장할 때만 새 버전으로 쓴다. 일괄 변환은 하지 않는다 (10년 사용 전제, 파일이 사용자 자산).
- 앱보다 높은 버전의 파일은 읽기 전용으로 열고 경고한다.
- SQLite 색인은 `meta.schema_version`이 다르면 통째로 재생성한다 (느린 나이테 방식).
- 필드 추가는 마이그레이션 없이 가능하다 (없으면 빈 값). 필드 이름 변경·분리는 버전을 올린다.
- 컨텍스트 파일의 `version`은 별도다 (spec 문서). 데이터 모델 schema 1이 컨텍스트 파일 0.2를 만든다.
