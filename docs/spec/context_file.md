# 커리어 컨텍스트 파일 형식

> 버전: **v0.2** (2026-11-01). 변경 이력은 문서 끝.
> 상태: 실험 01(`docs/experiments/01_context_file_validation.md`, 3개 서비스 × 3개 활용 프롬프트)로 활용 방향(2절)은 검증됨. 구조화 응답 블록(3절)은 미검증.
> 근거: 2026-11-01 개발자 본인의 경력기술서를 수작업으로 분해해 만든 실데이터 파일(저장소 외부, 경험 25건, 약 42KB).
> 관련 결정: D-001(활용은 컨텍스트 파일 내보내기), D-008(기록 단계는 프롬프트 왕복).
> 이 문서는 두 가지 형식을 정의한다. ① 앱이 내보내는 **컨텍스트 파일**(AI에게 주는 것), ② AI가 앱에 되돌려 주는 **구조화 응답 블록**(앱이 파싱하는 것).

## 1. 용어 (04_DATA_MODEL에서 확정)

| 영문 | 한국어 | 비고 |
|------|--------|------|
| Career | 경력 | 회사 / 조직 / 직위 / 기간. ID `C-nn` |
| Project | 과제 | 선택 계층. ID `P-nn` |
| Experience | 경험 | STAR 단위. ID `E-nnn` |
| Entry | 기록 | 사용자가 쓴 원문. 경험의 재료 |
| Skill | 역량 | 축 4개: 기술 / 업무 / 리더십 / 문제해결 |
| Evidence | 증빙 | 특허, 수상, 문서, 링크 |

STAR의 T는 "과제"가 아니라 **"목표"**로 부른다. Project의 한국어 이름 "과제"와 겹치기 때문이다. (확정 필요)

## 2. 컨텍스트 파일 (앱 → AI)

### 2.1 전체 구조

```markdown
---
format: slow-way-career-context
version: 0.1
exported_at: YYYY-MM-DD
owner: 이름 또는 익명
scope: 전체 | 경력 C-nn | 기간 | 선택
anonymized: true | false
experience_count: N
---

# 사용 안내 (AI에게)
# 프로필
# 경력 (역순, 표)
# 과제 (표, 선택)
# 경험 (STAR, 시간순)
  ## [E-001] 제목
# 역량 색인 (표: 축 | 역량 | 관련 경험)
# 정량 성과 목록 (표: 지표 | 값 | 비교 기준 | 시점 | 경험)
```

### 2.2 사용 안내문 (파일 상단 고정)

실험 01에서 세 서비스 모두 이 안내문의 수치 규칙을 지켰다 (9회 모두 수치 보존 만점). 근거 ID 규칙도 세 서비스가 지켰고 채점 시간을 크게 줄였다.

```markdown
- 이 문서는 사용자가 직접 기록하고 검토한 경력 데이터다.
- 여기에 없는 성과, 수치, 역할, 직위를 만들지 않는다.
- 수치는 문서에 적힌 값과 비교 기준만 사용한다. "기준 없음"으로 표시된 수치는 비교 표현(개선, 단축, 증가)을 붙이지 않는다.
- 추정이 필요하면 문장을 만들지 말고 사용자에게 질문한다.
- 요청받은 문서 형식을 따르되, 각 문장은 아래 경험 ID 중 하나에 근거해야 한다. 결과물에는 근거 ID를 괄호로 남긴다. 예: (E-001)
- "확인 필요" 항목에 적힌 내용은 미확정이다. 그 내용을 단정하는 문장을 쓰지 않는다.
```

근거 ID는 최종 문서에서 사용자가 지워야 한다. 앱의 내보내기 화면에 "결과물에서 (E-nnn) 일괄 삭제" 안내 또는 도구가 필요하다.

```markdown
- 구분: 업무 | 업무 외
- 상태: 초안 | 구조화 | 확정

### 상황
### 목표
### 행동
- 항목
### 결과
- 정량: 지표 | 값 | 기준: … 또는 "기준 없음" | 시점: …
- 정성: …
- 비즈니스 영향: …
### 역량
- 기술: / 업무: / 리더십: / 문제해결:
### 교훈
### 증빙

```

01_PRODUCT_CONCEPT 5장의 모델과 다른 점:

| 항목 | 변경 | 이유 (실데이터 분해에서 확인) |
|------|------|------------------------------|
| **교훈** 필드 신설 | 추가 | 경력기술서의 "▶ 운영 원칙 / 위임에서 확인한 것" 같은 블록이 STAR 어디에도 안 들어감. 팀장급 문서에서는 이 부분이 설득의 핵심 |
| **구분** 필드 신설 | 추가 | 개인 앱 개발, 연구회 같은 업무 외 활동도 경험으로 넣되 구별해야 함 |
| **확인 필요** 필드 신설 | 추가 | 경력기술서에서 분해한 경험은 기간·역할·수치 기준이 빈 경우가 많다. 비운 채로 두고 확정 전에 채우게 한다 |
| 정량 결과를 `지표 | 값 | 기준 | 시점` 네 칸으로 | 구조화 | 115명, 16건, 11건처럼 비교 기준이 없는 수치와 62%→85%처럼 있는 수치가 섞여 있다. 기준이 없는 수치에 AI가 "개선"을 붙이는 것을 막아야 한다 |
| Evidence의 Documents/Images/Links 하위 구분 | 단순화 | v0.1에서는 한 줄 목록. 첨부는 앱 내부에만 두고 파일에는 이름만 |
| 역할 줄에 **수행 주체 구분** 규칙 (v0.2) | 추가 | 실험 01에서 "기획·검증, 구현은 AI 코딩 도구"를 AI가 "직접 구현"으로 격상(Gemini 3회). 역할 줄이 모호하면 활용 단계에서 사실 오류가 남 |

실험 01에서 확인된 효과: **교훈** 필드는 세 서비스 모두 자기소개서 각 이야기의 마무리 문장으로 사용했다. **확인 필요** 필드는 면접 질문 프롬프트에서 "약한 지점"과 "준비가 부족한 경험" 목록의 재료가 됐다. 정량 성과의 **기준 없음** 표기는 비교 표현 오용을 9회 모두 막았다.

### 2.4 크기

실데이터 25건 기준 약 42KB(약 22,000자, 프로필·표 포함). 경험 1건 평균 700~900자. 100건이면 9만 자 안팎이라 ChatGPT·Claude·Gemini의 파일 첨부 한도 안이다. 분할은 v0.1에서 다루지 않는다.

## 3. 구조화 응답 블록 (AI → 앱)

사용자가 AI 응답을 앱에 붙여넣으면 앱이 이 블록을 찾아 파싱한다. 기록 1건 구조화(`docs/prompts/structure_entry.md`)와 경력기술서 분해(`docs/prompts/decompose_cv.md`) 모두 같은 형식을 쓴다.

### 3.1 형식

````markdown
```slow-way
형식: slow-way-experience/0.1
제목: 연속 공정 표면 결함 실시간 탐지 AI 개발
기간: 2018 ~ 2019
회사: A사
조직: 품질 AI 개발팀
직위: 과장
역할: 실무 개발자 (문제 정의부터 운영 시스템 구현까지)
구분: 업무
상황: 표면 결함 판정을 규칙·통계 기반으로 하고 있었고 한계가 있었다. 사업 목표는 후공정 부하 절감이었다.
목표: 후공정 부하 절감에서 역산해 달성 가능한 탐지 성능 상한을 정하고, 미탐지율을 그 수준으로 관리하면서 오탐을 최소화한다.
행동:
- 결함 발생부의 온도 저하 특성에 착안해 온도 맵 위의 결함을 객체로 정의, CNN 객체탐지 문제로 재구성
- 시계열 특징 추출 및 시계열→이미지 변환 알고리즘 설계
- C# 기반 실시간 운영 시스템 직접 개발
결과_정량:
- 오탐지율 | 약 44% 개선 | 기준: 기존 규칙·통계 기반 판정 | 시점: 2019
- 등록 특허 | 3건 | 기준 없음 | 시점: 확인 필요
결과_정성: 연구개발본부 우수성과 포상(2019)
비즈니스_영향: 이후 AI 과제 심의 기준의 실질적 근거가 됨
역량_기술: 비전 AI 객체탐지, 시계열 특징 추출, C# 실시간 시스템
역량_업무: 연속 공정 이해, 품질 판정 체계
역량_리더십:
역량_문제해결: 문제 재정의, 사업 목표에서 성능 목표 역산
교훈: 직접 만들어 본 경험이 다른 팀 과제를 심의할 때의 설득력이 됐다.
증빙:
- 등록 특허 3건
- 연구개발본부 장려상(2019)
확인_필요:
- 시작·종료 월
- 특허 3건이 모두 이 과제의 것인지
```
````

### 3.2 규칙 (프롬프트에 그대로 들어감)

1. 블록은 반드시 ` ```slow-way ` 로 시작하고 ` ``` ` 로 끝낸다. 블록 밖의 설명은 자유롭게 써도 되며 앱은 무시한다.
2. 첫 줄은 `형식: slow-way-experience/0.1`.
3. 한 줄에 `키: 값`. 키는 위 목록의 이름만 쓴다. 값이 없으면 키만 남기고 비운다. 키를 빼지 않는다.
4. 목록 키(행동, 결과_정량, 증빙, 확인_필요)는 다음 줄부터 `- ` 로 시작하는 항목을 나열한다.
5. `결과_정량` 항목은 `지표 | 값 | 기준: … | 시점: …` 네 칸을 `|` 로 나눈다. 비교 기준을 모르면 `기준 없음`이라고 쓴다. 원문에 없는 수치를 만들지 않는다.
6. 원문에 없는 내용은 추정하지 않는다. 비어 있으면 `확인_필요`에 질문으로 적는다.
7. 경험이 여러 개면 블록을 여러 개 쓴다. 블록 하나에 경험 하나.

### 3.3 파서 설계 메모 (06_AI_DESIGN·05_TECHNICAL_DESIGN 재료)

- 줄 단위 파서. YAML 라이브러리를 쓰지 않는다. 한국어 값에 콜론·따옴표·`#`이 흔해 YAML은 깨진다.
- 키 비교는 공백과 밑줄을 지우고 한다 (`결과 정량` = `결과_정량`).
- 모르는 키는 버리지 않고 "미분류" 로 보관해 사용자에게 보여 준다.
- 블록을 하나도 못 찾으면: 응답 전체를 Entry 원문으로 보존하고, "형식 블록이 없습니다. 프롬프트를 다시 붙여넣으세요" 안내.
- 블록은 찾았지만 줄이 안 읽히면: 그 줄 번호와 원문을 보여 주고 나머지는 채운다.
- 정량 항목이 `|` 네 칸이 아니면: 값 전체를 "지표" 칸에 넣고 경고 표시.
- 파싱 가능 비율(블록 수 / 줄 수 기준)을 실험에서 서비스별로 측정한다.

## 4. 익명화 (내보내기 옵션)

치환 대상: 회사명, 조직명, 인명, 제품·공정명, 고객명, 특허 번호, 수상명의 회사명. 치환표는 앱에 보관하고 파일에는 `A사`, `B팀` 같은 자리표시자만 남긴다. v0.1 수작업 파일에서는 익명화하지 않았고, 저장소에는 이 문서의 3.1 예시처럼 익명화한 조각만 둔다.
